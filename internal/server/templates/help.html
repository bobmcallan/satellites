Roles

Three roles act on a story. Each has a fixed boundary the server enforces at the verb layer — not by convention, and not something an agent can talk its way around.

Executor

The agent doing the work. It holds an executor api-key. It can create stories and edit story bodies. It cannot change a story's status or write the ledger.

When it judges its work ready, it calls story_request_review. It does not mark its own work complete — it signals ready, and the gate decides.

Reviewer

The gate. The only role that can change a story's status and append the ledger.

A reviewer key is minted for a single review, used to run the gate skill, then revoked. The agent never holds a reviewer key, so it can never approve its own work.

Operator

The human. Acting through the CLI or the signed-in portal, the operator has full access.

The role gate applies only to api-key callers, so operator actions pass through it.

The status gate

A story advances only when a reviewer accepts it. Status never moves because an agent decided it was done.

  • The executor edits the body and calls story_request_review.
  • The verb mints a short-lived reviewer key and runs the gate skill named by the workflow for the current status.
  • On accept, the status flips to the next state and the ledger records it. On reject, the status stays put and the rejection notes land in the ledger.
  • The reviewer key is revoked when the review ends.

This is why a stalled or over-confident agent cannot declare success: it has no key that can move the status.
