Roles

Three roles act on a story. Each has a fixed boundary the server enforces at the verb layer — not by convention, and not something an agent can talk its way around.

Executor

The agent doing the work. It holds an executor api-key. It can create stories and edit story bodies. It cannot change a story's status or write the ledger.

When it judges its work ready, it runs satellites story review. It does not mark its own work complete — it signals ready, and the gate decides.

Reviewer

The gate. The only role that can change a story's status and append the ledger.

A reviewer key is minted for a single review, used to run the gate skill, then revoked. The agent never holds a reviewer key, so it can never approve its own work.

Operator

The human. Acting through the CLI or the signed-in portal, the operator has full access.

The role gate applies only to api-key callers, so operator actions pass through it.

The status gate

A story advances only when a reviewer accepts it. Status never moves because an agent decided it was done.

  • The executor edits the body and runs satellites story review.
  • The verb mints a short-lived reviewer key and runs the gate skill named by the workflow for the current status.
  • On accept, the status flips to the next state and the ledger records it. On reject, the status stays put and the rejection notes land in the ledger.
  • The reviewer key is revoked when the review ends.

This is why a stalled or over-confident agent cannot declare success: it has no key that can move the status.

The workflow monitor

The gate keeps the loop honest while it runs. The monitor is how an operator sees what the loop actually did — the declared process held against the recorded fact. It only ever reads: it never writes a ledger row and never moves a status, so watching the work can't perturb it.

Per-story trace

Each story's page (/stories/{id}) overlays the declared workflow — its states, transitions, and the gate on each edge — with the actual path taken, read from the ledger. Every transition shows whether its gate was accepted, rejected, fired, or never reached.

The view updates live: as a gate fires, the trace region refetches off the shared event bus, with no page reload.

Open engagements

satellites work status lists what each agent session is engaged on — the story, its phase, and whether the engagement lease is still fresh. It reads the per-repo engagement store; the START-door hook reads the same store to decide whether a file edit may proceed.

QA evidence

satellites evidence show <story> prints a story's durable QA trail — every gate run captured automatically by the reviewer loop, plus the CI outcomes recorded with satellites evidence ci (test / release / deploy → success / failure). The full trail is reconstructable after the fact, out of band from the agent's turn.

Loop audit

satellites evidence audit [story] walks the captured ledger trail and flags loop anomalies — an ungated deploy, a ship with no gate, status drift, unengaged work, a spurious enact-failure reject, or a rejection with no follow-up. With a story id it audits that one story; with none it sweeps the whole project. Findings surface to the operator only — never the executor's turn.

Tasks

Not all work is a story. A task is a governed, re-runnable runner — a repeatable job, run on demand or on a schedule, that records each run. A story is one-off work driven to done once; a task is work that recurs, or whose output is dated or versioned per run.

  • A task's body states the action, the output, and how success is verified — that is the work, judged by the same reviewer model that gates a story.
  • Re-run it whenever its inputs change; each run is recorded and the task's ## Report captures the outcome, so the history is reconstructable.
  • A task MAY name a reusable skill it invokes — but that skill is a capability in the executing agent's environment, not substrate the server resolves.
  • Choose a task (not a story) when the work recurs or its output is per-run/dated; choose a story for a single deliverable. Picking the primitive is the agent's job, from the shape of the work.

Codegraph

The codegraph is the high-level structure of a codebase — one node per package, one edge per intra-module import (“not function contents”). The binary emits the facts; the substrate renders them, and the project page shows them as an interactive graph.

  • Generate & query (local CLI). satellites code graph walks the working tree fresh each run — no stored index. Query it instead of eyeballing the dump: --package <p> (direct dependencies and dependents), --rdeps <p> (blast radius — who imports <p>, transitively), --deps <p> (what it pulls in), --cycles; each composes with --json. Test scaffolding is excluded by default (--include-tests to restore).
  • Maintain. The project's standing Codegraph task re-renders the graph and publishes a type:codegraph document — re-run it whenever the structure changes (it overwrites the current-state snapshot; git holds history). The published body carries the graph as a machine-readable codegraph JSON block plus a mermaid diagram and package table, stamped with a generated_at time and short git revision so staleness is visible.
  • View. The project page renders the published codegraph as an interactive pan / zoom / filter graph — click a package to focus its neighbourhood. A project with no codegraph renders cleanly.
  • Local vs MCP. Generation and query are local-only (the remote MCP server has no working tree, so there is no MCP code-search/generate verb). The MCP-reachable surface is the published type:codegraph document — document_list {tags:["type:codegraph"]} then document_get, or semantic_search.
