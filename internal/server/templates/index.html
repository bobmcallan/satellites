A reviewer-gated harness for agentic engineering.

As AI moves from stateless prompt-response to autonomous agents that determine their own path over time, systemic failures emerge. Agents loop endlessly, run down wrong roads, stall, or declare success on a stalled task. These are rarely problems with the underlying model — they are failures of the harness.

Harness engineering optimises four levers: context, tools, loop, governance. Satellites is opinionated about all four.

The four levers

1 · Context

what the model sees

The complete state-space available at the millisecond the model picks its next action — system prompts, prior execution steps, retrieved documents, memory, active variables.

Failure mode
Missing, contextually disconnected, or over-saturated — bloat buries the high-priority signal.
Architecture lens
The right information, shaped precisely, injected at the right moment.

2 · Tools

what the model can do

The exposed action surface that lets a text-generation engine execute state changes — codebase endpoints, MCP, sandboxed CLIs.

Failure mode
Raw integrations without semantic schemas, or unstructured shells with no safety boundary.
Architecture lens
Tools packaged as precise, self-describing schemas tailored to one capability boundary.

3 · Loop

how the agent runs

Intake context → execute tool → interpret output → evaluate continuation → repeat until complete.

Failure mode
Runaway chains, infinite generation, false-positive completion when the task has stalled.
Architecture lens
Deterministic wrapper assertions — step counts, timeouts, progression detection, definitive exit states.

4 · Governance

what boundaries it has

Permissions, sandboxes, environment limits, audit logging, human-in-the-loop approval gates that keep automated actions safely bounded.

Failure mode
Broad write/delete permissions without verification — or restrictions so tight the agent can't make necessary updates.
Architecture lens
Separated permissioned boundaries — deciding what runs autonomously vs. what requires a hard stop.

How Satellites realises the four levers

Satellites does not let a single model manage an open-ended loop over a giant context window. The framework is built around a single load-bearing premise: Separation of roles is structural, not advisory.

Context → The satellite as an isolated sub-harness — a dedicated compartment with a minimised context surface. Stories are the working spine; the ledger is bookkeeping the model needn't read most of the time.
Tools → Packaged capability through document_* / variable_* / project_* / apikey_* verbs over MCP, plus operator-authored skills. Skills are pure capability — they report, they do not decide what the result means.
Loop → Orchestrated phases. The executor has two verbs — start and done — and cannot mark its own work complete. No runaway loops, no false-positive completion.
Governance → Embedded reviewers as the gate — agent · static · external · process · composite. Only reviewers can change story status. Scopes (system, workspace, project) gate the verb layer.

The state machine

Each phase has three states. Reviewer accept advances. reject returns the phase to in-progress with notes. accept_with_additional_phase inserts a new phase before the next — the workflow adapts without the executor deciding to skip.
