What's real today

Reviewer-gated state machine

Three states per phase — pending → inprogress → done. Accept moves; reject loops back with its reason. The dispatcher refuses to advance an ambiguous transition rather than guessing, and a workflow with an unbounded loop is rejected when it's parsed.

Two kinds of gate

A gate is either an LLM reviewer judging the work against an operator-authored contract, or a deterministic command whose exit code selects the pass or fail edge (lint, tests, schema validation). Soft judgement and hard stops, in the same machine.

A durable evidence trail

Every gate run and CI outcome is written as a qa_evidence record — decision, from/to status, the reject reason, and the commit it ran against. The record is the audit log and the metric source, not a console line that scrolls away.

Bounded retry with recovery

Repeated rejects on the same edge spend a quota and block the story; a recovery gate brings it back with a fresh quota. Loops on trivia are the contract being enforced, not a defect.

Roles enforced at the verb layer

Executor, reviewer, and operator hold different keys, and the server — not a policy document — rejects an executor that tries to approve its own work. The reviewer key is minted per review and revoked after it.

MCP gateway + live portal + code indexing

Stories, documents, projects, variables, the ledger, and the reviewer surfaces are scope-checked MCP verbs; the portal renders stories, gate verdicts, the evidence trail, and a code graph in real time. Satellites indexes the target repo — symbol map and semantic search — so a reviewer judges against the actual codebase.

The state machine

Each phase has three states. Reviewer accept advances. reject returns the phase to in-progress with notes. accept_with_additional_phase inserts a new phase before the next — the workflow adapts without the executor deciding to skip.

Why not just a workflow runner or an agent harness

A workflow runner sequences steps and trusts each step to report its own success. An agent harness tunes context, tools, and the loop — and then lets the agent decide it's finished. Satellites' difference is the one thing neither does: the actor that produces the work is structurally barred from being the actor that accepts it, and the acceptance is recorded. That single boundary turns "the agent said it's done" into "the work passed a gate, and here is the record."

install the client

The satellites CLI is a per-platform release binary, installed the way claude install works — client only, no server. The one-line bootstrap fetches the installer, sha-verifies the platform binary, and places it at ~/.local/bin/satellites (on PATH):

curl -fsSL https://github.com/bobmcallan/satellites/releases/latest/download/install.sh | sh

Pass --local for the in-repo dev binary, or --version <tag> to pin a release (sh -s -- --local). Once satellites is on PATH, satellites install / satellites update place and refresh the same binary.

out of the box

Install the client, ask the agent to set the repo up, and drive a story to done — with nothing in .claude/skills:

satellites init     # bind: .satellites/satellites.toml (active server_url + project_id
                    #   resolved from your git remote) and .mcp.json (mcpServers.satellites
                    #   → <server_url>/mcp — the SAME server as the toml) + the harness hooks
satellites auth     # browser login → executor key in the user credential store
satellites status   # → db UP, MCP connected — no flags, no hand-edits

init is idempotent — it reports added-vs-present, upgrades an existing toml rather than clobbering it, and derives the MCP endpoint from the toml's server_url, so the CLI and the agent's MCP client can never point at different servers. If the project isn't resolvable yet, init prints the one follow-on command (satellites project match --remote <git-remote>) to bind project_id once authenticated.

Then create a story and let the agent drive it through its reviewer-gated workflow:

satellites work init <story-id>                              # engage the workflow
satellites story status_transition --skill <gate> <story-id> # reviewer-gated transition
satellites story set-status <story-id> done                  # advance an ungated edge

.claude/skills holds no gates by default: reviewer skills resolve local → embed → server, so a fresh repo is governable empty. The baseline workflow gates the entry transition with the spine reviewer satellites-intent-plan-review, resolved from the binary embed — but it is ordinary, editable substrate: a repo MAY override it (or any reviewer) by authoring .claude/skills/<name>, which the resolver consults first. The agent's goal is simply to reach done through the transitions its workflow declares.
